# Plan: Substance Library (ECHA, CMR, CLP, GHS) for Management Portal

## Goal
Set up a **Substance Library** within the Management Portal under the ECHA section. This is an **offline, no-API** module that stores and manages chemical substances, classifications, and regulatory references for internal compliance use.

## Scope
The system is a **FastAPI + PostgreSQL + Vanilla JS** monolith (no Next.js/Prisma migration needed). We will build the Substance Library by adding new tables, API routes, and UI sections into the existing codebase.

## What the User Wants
The user explicitly requested **5 libraries**:
1. **Substance Library** — core chemical registry (CAS, EC, names, status).
2. **CMR** — Carcinogenic, Mutagenic, Reprotoxic classifications.
3. **ECHA** — ECHA/REACH registration data, SVHC status.
4. **CLP** — Classification, Labelling & Packaging (hazard classes, categories, statements).
5. **GHS** — Globally Harmonized System pictograms, signal words, hazard statements.

Additionally, **Symbol References** — a reference table for GHS/CLP hazard pictograms and their meanings.

## Understanding of the Current Architecture
- **Backend:** FastAPI (`backend/main.py`, `backend/bom_routes.py`).
- **ORM:** SQLAlchemy with models in `backend/pipeline/models/database.py` and `backend/models.py`.
- **DB:** PostgreSQL (also SQLite fallback in some pipeline parts).
- **Frontend:** Single static HTML file `static/management.html` with vanilla JS.
- **Auth:** JWT-based (`auth_helpers.py`), same token system used across all tabs.
- **Existing ECHA tables:** `echa_chemicals`, `echa_compliance_checks`, `svhc_substances`, `svhc_compliance_checks` already exist.

## Proposed Milestones

### Milestone 1 — Database Schema (SQLAlchemy Models)
**Goal:** Create the 5 library tables + symbol reference table in the existing SQLAlchemy model file.

**Tables to add:**
| Table | Purpose |
|---|---|
| `substance_library` | Master substance registry (name, CAS, EC, molecular formula, IUPAC, source URL, registration status, etc.) |
| `cmr_substances` | CMR-specific fields linked to `substance_library` (CMR type, category, hazard class, CLP notes, ATP ref) |
| `echa_substances` | ECHA/REACH details linked to `substance_library` (REACH status, tonnage band, registration type, index number, CLP notes, ATP ref) |
| `clp_classifications` | CLP hazard data linked to `substance_library` (hazard class, category, H-statement code, P-statements, signal word, pictograms, conc. limits, M-factor) |
| `ghs_classifications` | GHS-specific data linked to `substance_library` (GHS hazard class, category, pictogram codes, signal word, hazard statements, precautionary statements) |
| `symbol_references` | Static reference for hazard pictograms (symbol code, name, description, image URL/emoji, regulation source) |

**Design principle:** `substance_library` is the **master table**. All other tables (`cmr_substances`, `echa_substances`, `clp_classifications`, `ghs_classifications`) have a **nullable FK** to `substance_library.id` so a substance can exist in one or multiple libraries independently, and cross-linking can happen later.

**Where to add:** `backend/pipeline/models/database.py` (to keep with existing ECHA/SVHC tables) or a new `backend/substance_library/models.py`. I recommend adding to `backend/pipeline/models/database.py` for consistency with existing ECHA tables.

### Milestone 3 — REST API Endpoints
**Goal:** Build CRUD + search endpoints for all 5 libraries and symbol references.

**Base path:** `/api/substances/` (new router, not under `/api/bom/` to keep it clean).

**Endpoints:**

#### Substance Library (Master)
- `GET /api/substances` — list all substances (pagination: `page`, `limit`, `limit=all`)
- `GET /api/substances/{id}` — get single substance with all linked data
- `POST /api/substances` — create substance
- `PUT /api/substances/{id}` — update substance
- `DELETE /api/substances/{id}` — delete substance + cascade to linked tables
- `GET /api/substances/search?q=` — global search across names, CAS, EC numbers

#### CMR Library
- `GET /api/substances/cmr` — list CMR substances
- `POST /api/substances/cmr` — add CMR entry (linked to master or standalone)
- `PUT /api/substances/cmr/{id}` — update
- `DELETE /api/substances/cmr/batch` — batch delete (admin password required, following existing pattern)

#### ECHA Library
- `GET /api/substances/echa` — list ECHA/REACH substances
- `POST /api/substances/echa` — add
- `PUT /api/substances/echa/{id}` — update
- `DELETE /api/substances/echa/batch` — batch delete

#### CLP Library
- `GET /api/substances/clp` — list CLP classifications
- `POST /api/substances/clp` — add
- `PUT /api/substances/clp/{id}` — update
- `DELETE /api/substances/clp/batch` — batch delete

#### GHS Library
- `GET /api/substances/ghs` — list GHS classifications
- `POST /api/substances/ghs` — add
- `PUT /api/substances/ghs/{id}` — update
- `DELETE /api/substances/ghs/batch` — batch delete

#### Symbol References
- `GET /api/substances/symbols` — list all symbol references
- `POST /api/substances/symbols` — add new symbol (admin only)
- `PUT /api/substances/symbols/{id}` — update
- `DELETE /api/substances/symbols/{id}` — delete

**Pagination format (existing convention):**
```json
{
  "data": [...],
  "pagination": { "page": 1, "limit": 50, "total": 200, "totalPages": 4 }
}
```

**Where:** New file `backend/substance_routes.py`, registered in `backend/main.py`.

## Technical Decisions & Clarifications Needed

### 1. Where to place the new models?
**Options:**
- **A:** Add to `backend/pipeline/models/database.py` alongside existing ECHA/SVHC tables. **Pros:** Consistent, existing ECHA data is already there. **Cons:** File is getting large.
- **B:** Create `backend/substance_library/models.py`. **Pros:** Cleaner separation. **Cons:** Need to ensure same `Base` metadata and engine are used for table creation.

**Recommendation:** Option A for minimal friction, or Option B if user wants clear separation.

### 2. Should we reuse existing `echa_chemicals` table or create new `echa_substances`?
The existing `echa_chemicals` table is already populated and has UI wired up. The prompt's master schema defines a more detailed `Substance` model (with `iupacName`, `molecularFormula`, `tonnageBand`, etc.).

**Options:**
- **A:** Migrate/extend `echa_chemicals`. **Pros:** Keeps existing data. **Cons:** Migration complexity, existing fields may not match.
- **B:** Create new `substance_library` + `echa_substances` tables, and treat `echa_chemicals` as legacy. **Pros:** Clean slate matching the prompt spec. **Cons:** Existing ECHA UI needs updating.

**Recommendation:** Option B — create the new master `substance_library` and library-specific tables. Update the ECHA UI to use the new endpoints. The old `echa_chemicals` can remain for backward compatibility during transition, or be migrated later.

### 3. File upload format expectations?
The prompt mentions `update_echa_reach.py` scrapers. Since we have **no API access**, we should support:
- Manual CSV/Excel upload for each library.
- A **downloadable template** for each library so users know the expected columns.

**Recommended columns per upload template:**
- **Substance Library:** `name`, `cas_number`, `ec_number`, `iupac_name`, `molecular_formula`, `registration_status`, `source_url`
- **CMR:** `substance_id` (or `cas_number` for matching), `cmr_type`, `cmr_category`, `hazard_class`, `hazard_statements`, `clp_notes`
- **ECHA:** `substance_id` (or `cas_number`), `reach_status`, `tonnage_band`, `registration_type`, `index_number`, `clp_notes`, `atp_reference`
- **CLP:** `substance_id` (or `cas_number`), `hazard_class`, `hazard_category`, `hazard_statement_code`, `hazard_statement`, `pictograms`, `signal_word`, `precautionary_statements`, `m_factor`
- **GHS:** `substance_id` (or `cas_number`), `ghs_hazard_class`, `ghs_category`, `pictogram_codes`, `signal_word`, `hazard_statements`, `precautionary_statements`

### 4. GHS Pictogram representation?
Since there are no image assets for GHS pictograms in the repo:
- Use **Unicode emoji/symbol approximations** (e.g., ☠️ for toxic, 🔥 for flammable) in the Symbol Reference table.
- Allow `image_url` field for future upload of actual pictogram PNGs.
